  What's on your machine

  You have Node 26 and Docker. Neither PHP nor Go is installed, so whichever
  backend we pick runs in Docker or needs installing first.

  Proposed stack

  Layer: Frontend
  Choice: Vite + React + TypeScript, React Router, TanStack Query, CSS variables

    for Eneba's design tokens
  Why: It's fast to set up and each piece is easy to explain. TanStack Query
    handles caching and loading states.
  ────────────────────────────────────────
  Layer: Backend
  Choice: Go (chi router, pgx and sqlc, golang-migrate), REST with an OpenAPI
    spec
  Why: It builds to a single small binary, starts quickly on free hosting, and
    sqlc means we write plain SQL that you can explain line by line.
  ────────────────────────────────────────
  Layer: DB
  Choice: PostgreSQL with pg_trgm
  Why: Trigram similarity handles typos and partial names in search without
    needing Elasticsearch.
  ────────────────────────────────────────
  Layer: Types
  Choice: openapi-typescript generates frontend types from the API spec
  Why: The frontend and backend can't drift apart.
  ────────────────────────────────────────
  Layer: Deploy
  Choice: One Docker image on Render where Go serves the API and the built React

    app, with the database on Neon's free tier
  Why: One origin means no CORS problems and login cookies just work. Neon's
  free
    database doesn't expire, while Render's free Postgres expires after 30 days.

  Scope: three features to go deep on

  The brief says a few features done well beat many done minimally, so I'd put
  the extra effort here:
  1. Search: typo tolerance, autocomplete in the header, and results that stay
     in sync with the store's filters.
  2. Checkout correctness:
     - Keys are reserved inside a database transaction (FOR UPDATE SKIP LOCKED),
       so the same key can never be sold twice.
     - Payments can be retried safely without charging twice.
     - Stock always matches the number of available keys.
     - The buyer sees their key in order history.
  3. Homepage blocks: the backend sends a layout (an ordered list of blocks) and
     each block type has its own data source:
     - Banners come from a banners table.
     - Best sellers are calculated from orders.
     - Deals are calculated from offer discounts.

     The frontend only maps each block type to a component, so nothing is
     hardcoded. I'd build this as one backend with separate modules rather than
     real microservices, which is easier to defend in a review.

  Everything else gets solid but standard treatment:
  - Store: filters (platform, region, price, type), sorting, and pagination, all
    saved in the URL.
  - Product page: details plus a comparison of seller offers.
  - Cart: kept in the browser for guests and checked against the server at
    checkout.
  - Auth: email and password with bcrypt, using a JWT stored in a secure cookie
    that page scripts can't read.
  - Payment: a simulated payment provider. Certain test card numbers succeed and
    others fail, and it's built so Stripe's test mode could replace it later.

  Data model

  users, products (title, slug, platform, region, type, genres, image,
